> **v7.8 终审收口要点**：
> 1. **`OPEN` 态 `mark_pr_ready` 判定优先级钉死（无终结证据绝不脱离 `unknown_paused` 写锁）**：对 `PR.state == 'OPEN'`，恢复方**第一步先判旧请求终结证据**——凡缺失绑定该 `op_id` 的本地响应回执 `op.remote_receipt_id` 且无可信未发/确定性拒绝证据，**无论远端是否已被第三方标为 Ready、亦无论 `headRefOid`/`baseRefName` 是否已发生漂移，该操作状态一律保留 `unknown_paused`（绝不提前转入非未决态 `diverged_needs_human` 而释放写锁）**；若同时观测到头/基线漂移，额外标记单据 `needs-human` 并告警，同时继续持有 `unknown_paused` 写锁；
> 2. **主管换届对旧 `prepared_local` 的同事务退役与新 `op_id` 接管迁移**：主管在登记撤权提交 `prepared_local` 后、晋升前崩溃时，新主管（`new_dispatcher_epoch > row.owner_epoch`）持 `dispatcher.lock` 在同一 `BEGIN IMMEDIATE` 事务内确认旧记录仍为 `prepared_local`（零发送），将其翻转为终态 `superseded_by_retry` 并建立绑定新代数的新 `prepared_local` 记录；
> 3. **单一命名 `resolve_unit_scope_and_pending()` 严防传入 `pr_id` 覆盖已绑定 PR 且在 `set_current_candidate` 拦截兄弟单据 `prepared_local`**：① 事务内先核对 `work_units.pr_id`（及该单据已有非空 `external_ops.pr_id`），若传入的非空 `:pr_id` 与已绑定 PR 不一致直接抛错拒绝（严禁 `COALESCE` 覆盖导致漏掉真实兄弟单据）；② `set_current_candidate(unit_key, C)` 仅豁免即将同事务作废的**本单据自身**普通 `prepared_local`（`row.unit_key == :unit_key AND row.owner_kind == 'worker' AND row.status == 'prepared_local'`），对共享 PR 兄弟单据 B 名下的任何 `prepared_local`（含 `pr_id IS NULL`）一律计入阻塞数并原子拒绝切换；
> 4. **单 `op_id` 单 mutation、发前 `isDraft` 校验与发后/恢复对账后置条件冲突补救闭环**：`dequeue_pr` 与 `disable_pr_automerge` 独立授权、部分成功自动保锁；`clear_veto_and_resume` 校验不早于 `max_op_seq` 的同一 `eff_pr_id` 快照满足 `OPEN & isDraft == true & mergeQueueEntry == null & autoMergeRequest == null` 且本地未决数为 `0`；后续 Worker 发前重读显式校验 `state == 'OPEN' & isDraft == expected_is_draft & mergeQueueEntry == null & autoMergeRequest == null & headRefOid == expected_oid & baseRefName == authorized_base_ref`，观察到冲突即中止（`0` 次远端写入）并转 `needs-human`；对“发前重读通过后至服务端执行前”的窄窗口，服务端原子拒绝仅覆盖协议原生前置条件（`--force-with-lease` 校 OID、`expectedHeadOid: C` 校头提交），而**发后即时复核与崩溃恢复对账的检出承诺严格限定为“复核/对账读取时刻仍可观察到、且与该动作预期后置状态冲突”的远端状态**（如 `push_branch` 在已绑 PR 上虽成功推送 `OID == C`，但正常返回复核或恢复对账发现 `!isDraft` / 已入队 / 已开自动合并时，在结案该推送的同时必须经 `db.register_admin_revoke` 置 `veto_pending = 1`、转 `needs-human` 暂停后续发布并登记 `convert_pr_to_draft` 等独立补偿 `op_id`；而 `mark_pr_ready` 自身预期后置状态本就是 Ready，最终快照无法区分谁先翻转）。

## 2. 全环沙箱定义、对称裁判材料交接与 C 二进制传输契约

### 2.1 四类 `model_ring` 角色（`policy_manifest.json` `role_matrix`）
所有 `bwrap` 均带 `--die-with-parent --unshare-pid --unshare-ipc --unshare-uts --unshare-net --new-session --clearenv`；每轮新建洁净 `<sandbox_home>`，静态 `ap_sandbox_init` 与 `ap_safe_sh` 为不同 inode（宿主机动态 `/usr/bin/{bash,sh,dash}` 绝不进入 `model_ring`）：
- **`codex:issue_model`** / **`claude:issue_model`**：`/usr/bin/{bash,sh,dash}` 绑定 `ap_safe_sh`；`<worktree>/.git` 只读覆盖；Claude 固定加 `--setting-sources user --strict-mcp-config --exclude-dynamic-system-prompt-sections` 与双斜杠 `claude_permission_deny`；
- **`codex:readonly_model`** / **`claude:readonly_model`**：无 shell、无 `tool.sock`；对称挂载从不可变提交 `base_sha..C` 导出的只读 `/ap-review-bundle` 与可写 `outbox`；宿主机从 `outbox/verdict.json`（`codex:readonly_model`）或受控标准输出 JSON（`claude:readonly_model` 仅授 `Read/Glob/Grep` 无 `Write`/shell，固定走受控 stdout JSON）采集校验异构家族裁决后落 `review_receipts(C)`。

### 2.2 三类无网无凭据执行环（`policy_manifest.json` `execution_rings`）
三环一律 `--unshare-pid --unshare-ipc --unshare-uts --unshare-net --clearenv`，**绝不挂载 `sandbox_home` 或任何凭据**：
1. **`tool_ring`**：只读挂 `/usr`、基础 `/etc`、`<worktree>/.git`、`$MANAGED_GITDIR`、`$REPO_MAIN/.git/objects`、`trusted_base_cache`、`shell_snapshots`；可写仅 `<worktree>`（不含 `.git`）、每轮即弃 `ephemeral_tool_cache`、`<shared_tmp>`；
2. **`git_ops_ring`**：固定 `GIT_OPTIONAL_LOCKS=0` 与显式 `GIT_DIR` / `GIT_COMMON_DIR` / `GIT_WORK_TREE`；采样期 `MANAGED_GITDIR`、`$REPO_MAIN/.git/objects` 与 `<worktree>` 全只读，仅 `<run_dir>/scratch-objects` 与 `<run_dir>/stage_dir` 可写；
3. **`verify_ring`**：只读挂 `/proc`、`/dev`、`/usr`、基础 `/etc`、`$CLEAN_TREE` 与 `trusted_base_cache`（开启 `enable_ui_verify: true` 时额外只读挂 `/opt/google/chrome`，默认关闭；**绝不挂 `ephemeral_tool_cache`**）；唯一可写挂载 `<run_dir>/verify-out-<C>`（`cp -a --reflink=auto` 拷入，禁硬链接）。

### 2.3 C 二进制传输细节
- `ap_sandbox_init.c` 与 `ap_safe_sh.c` 5,000 ms 内对 `AF_UNIX` `EAGAIN` 关闭重连退避并强制校验 `getpeername(fd, ...) == 0`；代理并发上限 `PROXY_MAX_CHILDREN = 32`，`accept4` 瞬态容错，空轮询方向置 `fd = -1`。
- `ap_safe_sh.c` 解除 `SIGALRM` 屏蔽并校验 `setitimer(660s) == 0`；先收后发，终帧 `R:<0..255>\n` 后要求干净 `EOF`（或完整 `R:` 且零残留字节后的 `ECONNRESET`）；发出 `Z:0\n` 后保持 `sfd` 开启，对非 TTY `STDOUT_FILENO`/`STDERR_FILENO` 空缓冲时亦持续轮询（TTY 仅在缓冲非空时轮询），管道最后读端关闭（`POLLERR`）或 Unix 套接字完全 `close()`（`POLLHUP`/`POLLERR`）静默期立即关闭 `sfd` 退出 `141` 触发服务端 `killpg`（双向套接字仅 `shutdown(SHUT_RD)` 时于下次 `write -> EPIPE` 退出 `141`）。

## 4. 全入口统一关联集合锁、单变异补偿拆分与请求终结证据对账

### 4.1 提交起总时限 `pass_fds` 入口、`verify_unit_terminated()` 与物理/逻辑锁分离
1. **共用持锁启动入口**：Worker 用 `--no-block --collect`；阶段 3 清理用 `/usr/bin/timeout -s TERM -k 5s 85s systemd-run --user --wait --collect --no-ask-password -q --slice=app-autopilot.slice -p KillMode=control-group -p TimeoutStartSec=10s -p RuntimeMaxSec=60s -p TimeoutStopSec=10s ...`（`pass_fds=(flock_fd,)`，提交起总等待硬上限 90s）。
2. **`verify_unit_terminated(unit_name, expected_cgroup_dir)`**：恒存父目录 `user@<uid>.service` 锚点，`ActiveState in ('inactive','failed') & MainPID == '0'`，目录存在时校验 `ControlGroup` 一致、`cgroup.procs` 空且 `populated 0`，目录 `ENOENT` 且 `ControlGroup == ''` 时接受 `not-found + inactive` 或 `loaded + inactive/failed`（`reset-failed`），其余显式返 `False`。
3. **物理释放与逻辑写锁分离**：阶段 3 核验 `rc == 0`、`verify_unit_terminated == True`、`git status --porcelain=v1 --ignored=matching -z == b""` 与 `git clean -nffdx == b""` 后，阶段 4 置 `leases = 'free'` 仅释放物理资源；逻辑写锁由下方全入口唯一共用的 `resolve_unit_scope_and_pending()` 持续拦截。

### 4.2 五入口唯一共用 `resolve_unit_scope_and_pending()`、单 `op_id` 单 mutation 与全 10 类动作对账
1. **`db.py` 独占的唯一关联单据集合查询 `resolve_unit_scope_and_pending(unit_key, pr_id=None, statuses=('prepared_local','in_flight','unknown_paused'), exclude_op_id=None, exclude_self_worker_prepared=False)`**：
   - 在同一 `BEGIN IMMEDIATE` 事务内：
     ① **防覆盖 PR 身份核验**：读取 `bound_pr_id = (SELECT pr_id FROM work_units WHERE unit_key = :unit_key)`（单据不存在直接报错拒绝）及该单据历史非空操作 PR 集合 `SELECT DISTINCT pr_id FROM external_ops WHERE unit_key = :unit_key AND pr_id IS NOT NULL`；**凡存在两个不同非空 PR 身份，或传入 `:pr_id IS NOT NULL` 且 `bound_pr_id IS NOT NULL` 但 `:pr_id != bound_pr_id`，立即抛 `ScopeConflictError` 原子拒绝**（绝不用 `COALESCE(:pr_id, bound_pr_id)` 覆盖已绑定 PR）；取唯一有效 `eff_pr_id`（首次关联新 PR 时同事务写入 `work_units.pr_id = eff_pr_id`）；
     ② **完整关联单据集合展开**：**`scope_units = SELECT unit_key FROM work_units WHERE unit_key = :unit_key OR (:eff_pr_id IS NOT NULL AND pr_id = :eff_pr_id) UNION SELECT DISTINCT unit_key FROM external_ops WHERE :eff_pr_id IS NOT NULL AND pr_id = :eff_pr_id`**；
     ③ **未决计数与单调变更序号**：计算 **`pending_cnt = SELECT COUNT(*) FROM external_ops WHERE (:exclude_op_id IS NULL OR op_id != :exclude_op_id) AND NOT (:exclude_self_worker_prepared AND unit_key = :unit_key AND owner_kind = 'worker' AND status = 'prepared_local') AND (unit_key IN (:scope_units) OR (:eff_pr_id IS NOT NULL AND pr_id = :eff_pr_id)) AND status IN (:statuses)`**、`any_veto = SELECT COALESCE(MAX(veto_pending), 0) FROM work_units WHERE unit_key IN (:scope_units)` 及关联集合最大操作变更序号 `max_op_seq`；
   - **五个写入口强制统一复用 `resolve_unit_scope_and_pending()`**：
     - `claim_and_reserve`：要求 `any_veto == 0` 且三态 `pending_cnt == 0`；
     - 普通 `prepare_op`：要求 `any_veto == 0` 且三态 `pending_cnt == 0`（传入非空 `pr_id` 与已绑定 `bound_pr_id` 冲突时步骤①直接拒绝）；
     - `promote_op_to_in_flight`：普通 `worker` 分支排除自身 `op_id` 后要求 `row.status == 'prepared_local' & row.claim_epoch == active_claim_epoch & any_veto == 0 & 三态 pending_cnt == 0`（且候选绑定操作满足 `current_candidate_sha == row.candidate_sha`）；主管 `supervisor_admin` 分支要求持 `dispatcher.lock` 且 `row.status == 'prepared_local' & row.owner_epoch == current_dispatcher_epoch & any_veto == 1`、`scope_units` 全部活跃 Worker 均已核实 `verify_unit_terminated == True`、关联集合内**零任何 `in_flight` 记录**且**零同 `op_type` 的 `unknown_paused` 记录**；
     - `set_current_candidate`：启用 `exclude_self_worker_prepared=True`，要求 `any_veto == 0` 且 `pending_cnt == 0`（共享 PR 兄弟单据 B 的普通 `prepared_local` 即使 `pr_id IS NULL` 亦使 `pending_cnt >= 1` 而被拒绝）；
     - **`clear_veto_and_resume(unit_key, pr_snapshot=None)`（联合远端解封快照门禁与分层并发保证边界）**：对已绑定 PR 的撤权，主管总是确保 PR 退回草稿态（按需登记 `dequeue_pr`、`disable_pr_automerge` 与 `convert_pr_to_draft`，GitHub 原生禁止 Draft PR 入合并队列）；解封时调用方须在关联集合全部撤权操作结案（取当时单调序号 `snapshot_seq`）后经 `github_flow.fetch_pr_unveto_snapshot(eff_pr_id)` 读取同一 PR 的实时快照 `pr_snapshot`，随后 `db.clear_veto_and_resume` 在同一 `BEGIN IMMEDIATE` 内调用 `resolve_unit_scope_and_pending` 核验：① 本地三态 `pending_cnt == 0`；② 若 `eff_pr_id IS NOT NULL`，强制要求 **`pr_snapshot is not None & pr_snapshot.pr_id == eff_pr_id & pr_snapshot.snapshot_seq >= max_op_seq & pr_snapshot.state == 'OPEN' & pr_snapshot.isDraft is True & pr_snapshot.mergeQueueEntry is None & pr_snapshot.autoMergeRequest is None`**（采集序号不早于 `max_op_seq`；任一字段不符或拉取失败一律拒绝解封并保留 `veto_pending = 1`），通过后才将 `scope_units` 全部置 `veto_pending = 0`。**跨系统分层并发保证边界声明**：① `clear_veto_and_resume` 保证本地操作全部终结且在最后一次解封快照读取时刻 PR 处于 `OPEN + Draft + 队列为空 + 自动合并关闭`；② 后续任何 Worker 消费 `SendGrant` 执行 PR 相关远端写操作前，`github_flow.py` 强制重读实时 PR 快照并校验 **`state == 'OPEN' & isDraft == expected_is_draft & mergeQueueEntry is None & autoMergeRequest is None & headRefOid == expected_oid & baseRefName == authorized_base_ref`**（其中解封后预期仍为草稿态的 `push_branch`/`mark_pr_ready` 等动作强制 `expected_is_draft == True`，仅当前候选自身已完成 `mark_pr_ready` 后的 `enqueue_pr`/`merge_pr` 为 `expected_is_draft == False`）——**凡发前重读观察到任一冲突（包括第三方仅将 PR 标为 Ready 而未入队且 `headRefOid` 未变），立即中止发送（`0` 次远端写入）并将单据转 `needs-human`**；③ 对“最后一次发前重读通过后、实际远端请求执行前”的窄网络窗口，服务端原子拦截严格限定于各传输协议原生支持的前置条件——`push_branch` 由 `--force-with-lease=<authorized_head_ref>:<expected_oid>` 原子拒绝目标 ref 的预期 OID 漂移，`merge_pr`/`enqueue_pr` 由 `expectedHeadOid: C` 原子拒绝头提交漂移；④ 对协议无服务端草稿前置条件的窄窗口变更，**发后复核与崩溃恢复对账所能检出的范围严格限定为“复核/对账读取时刻仍可观察到、且与该动作预期后置条件冲突”的状态**（例如 `push_branch`/`create_draft_pr` 预期后置状态要求 `isDraft == True & mergeQueueEntry is None & autoMergeRequest is None`，正常返回复核与恢复对账一旦观察到 PR 为 Ready/入队/开自动合并，均通过 `db.register_admin_revoke` 置 `veto_pending = 1`、转 `needs-human` 暂停后续发布并登记独立 `convert_pr_to_draft` 等补偿 `op_id`；而 `mark_pr_ready` 的预期后置状态本身即为 `!isDraft`，单凭最终 Ready 快照无法区分我方请求与第三方谁先翻转）。
2. **每个 `op_id` 唯一单个远端 mutation、一次性 `SendGrant` 与入队归属规则**：
   - **拆分单变异主管动作（`one_mutation_per_op_id: true`，共 10 类动作）**：主管补偿拆分为三个各自只调用**单一 GraphQL mutation** 的原子动作——`convert_pr_to_draft`（`convertPullRequestToDraft`）、**`dequeue_pr`（`dequeuePullRequest(id=pullRequestId)`）** 与 **`disable_pr_automerge`（`disablePullRequestAutoMerge(pullRequestId)`）**！撤权时按需分别创建各自独立的 `op_id`、独立经 `promote_op_to_in_flight` 取得各自的 `SendGrant(granted=(rowcount==1))`、独立持久化各自的 `remote_receipt_id`；若第一项（如 `dequeue_pr`）已成功落回执结案为 `succeeded_verified`，而第二项（如 `disable_pr_automerge`）响应丢失处于 `unknown_paused`，`resolve_unit_scope_and_pending` 因第二项未决自动继续持有 PR 写锁；即便两项先后各自结案，最后执行 `clear_veto_and_resume` 时仍须通过上方绑定 `eff_pr_id` 的实时联合快照核验（`OPEN & isDraft == true & mergeQueueEntry == null & autoMergeRequest == null`）方可解封！
   - **入队归属判据 `is_enqueue_attributable_to_op(op, pr)`**：已落 `op.remote_receipt_id` 时按回执精确匹配；未落回执但 `PR.state == 'OPEN'` 且当前仍在队列（`mergeQueueEntry != null`）时，仅当 `mergeQueueEntry.enqueuer.login == bot_login & PR.headRefOid == op.candidate_sha & PR.baseRefName == op.authorized_base_ref & mergeQueueEntry.enqueuedAt >= op.prepared_at` 且期间无其他入队事件时判为可归属并补写 `op.remote_receipt_id = mergeQueueEntry.id`；若 `PR.state == 'MERGED'` 且事前无本地已持久化的 `op.remote_receipt_id`，历史时间线事件一律不作归属依据（判为 `superseded_by_pr_merge`）。
   - `SendGrant(granted=False)` 的并发落败者仅允许只读查询状态，严禁发网或触发对账；任何 `in_flight` 唯有在获权发送者自身完成传输返回后，或恢复方确证原发送者已失去发送能力（Worker 握 `.flock` 实查 `verify_unit_terminated == True`；主管持 `dispatcher.lock` 且 `current_dispatcher_epoch > row.owner_epoch`）后才允许对账。
3. **覆盖旧 `prepared_local` 与已证未发 `in_flight` 的主管换届接力（`replace_admin_op_for_retry`）**：
   - `register_admin_revoke` 在单一 `BEGIN IMMEDIATE` 事务内将 `scope_units` 全部置 `veto_pending = 1`、作废 `scope_units`/`eff_pr_id` 下全部普通 `prepared_local`，并按需插入单变异主管 `prepared_local` 记录（`dequeue_pr` / `disable_pr_automerge` / `convert_pr_to_draft`）；
   - **新主管（`new_dispatcher_epoch > row.owner_epoch`）持 `dispatcher.lock` 接管迁移规则**：
     1. **旧主管记录仍为 `prepared_local`（登记提交后、晋升前崩溃，确证零发送）**：`replace_admin_op_for_retry()` 在同一 `BEGIN IMMEDIATE` 事务内校验该旧记录 `status == 'prepared_local'`，**将其条件翻转为终态 `superseded_by_retry` 并同时插入绑定 `new_dispatcher_epoch` 的新 `new_op_id`（`status = 'prepared_local'`）**——旧 `op_id` 零发送且不再阻断后续解封，新 `new_op_id` 正常晋升至多发送一次！
     2. **旧主管记录已为 `in_flight` 或 `unknown_paused`**：先对账；唯有具备本地已持久化的绑定响应回执 `bool(op.remote_receipt_id)`（证明该旧请求已返回终结）且远端达标时才结案为 `succeeded_verified`；唯有具备可信未发送/确定性拒绝证据时才标 `not_executed`（远端已达标）或经 `replace_admin_op_for_retry()` 退役旧记录建新 `new_op_id` 重发（远端未达标）；**凡旧请求终结状态不明（仅有 PR 快照，无论第三方是否已抢先达标），一律保留 `unknown_paused` 写锁**！

3. **七步无损切换**：冻结旧入口 → 实查 100% 排空 → 备份保 `mtime` → 导入单据分离 HEAD 并写墓碑 → 真实 `probe` + `dispatch --dry-run` → 逐项目真实资源手动走通 `run-once` → 开启唯一 `agent-autopilot-dispatch.timer` 并核验前 3 轮触发。
